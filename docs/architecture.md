# 아키텍처

대상 독자: 이 저장소에 단계를 추가하거나 화면을 붙이는 사람.

## 요약

- 저장소는 커널(`src/`), WASM 빌드(`wasm/`), 웹(`web/`) 세 층입니다. 위 층은 아래 층을 읽기만 합니다.
- 수치 코드는 커널에만 있습니다. WASM 진입점은 타입을 고정하고 대안 번호를 커널 함수로 바꾸기만 합니다.
- 화면이 필요한 정보(함수, 조작 값, 대안, 소스 위치)는 빌드가 만든 목록 파일에서 나옵니다.
  손으로 쓰는 목록은 없습니다.

## 커널은 평평한 모듈 하나다

`src/GridToPINN.jl`이 `src/stepN/*.jl`을 순서대로 `include`합니다. 단계별 하위 모듈은 두지 않습니다.
뒤 단계가 앞 단계 함수를 그대로 부르는 것이 이 튜토리얼의 핵심이기 때문입니다.

| 재사용 | 만든 곳 | 쓰는 곳 |
|---|---|---|
| `top_speed`, `resistance` | `step1/drs.jl` | `step2/acceleration.jl` (출발 속도, 저항) |
| `euler_step`, `rk4_step` | `step2/integrators.jl` | `step3/simulation.jl` (확산의 시간 전진) |

파일은 함수 묶음 단위로 나눕니다. 화면이 파일이나 함수 단위로 소스를 보여주기 때문입니다.
커널 패키지에는 의존성이 없습니다. `Project.toml`에는 테스트용 `Test`만 있습니다.

커널을 쓸 때의 규칙은 네 가지입니다.

1. `T<:AbstractFloat`에 대해 일반적으로 씁니다. Float64 리터럴 대신 정수 리터럴이나 `T(...)`를 씁니다.
2. 타입이 안정적이어야 합니다. WasmTarget은 동적 디스패치를 컴파일하지 못합니다.
3. 나쁜 선택은 예외가 아니라 나쁜 수(NaN, Inf, 진동)로 나타나야 합니다. "깨뜨리기" 문항이 이것을 보여줍니다.
4. 대안 지점은 같은 서명을 가진 함수들로 만듭니다. 예: `diffusion_euler_step`, `diffusion_rk4_step`,
   `diffusion_cn_step`은 모두 `step(u, t, Δt, α, dx)`입니다.

시뮬레이션은 3단계부터 상태 구조체를 씁니다(`Diffusion1D`). 화면이 "만들기, n걸음 전진, 장 꺼내기,
오차 꺼내기"로 나눠 부르기 때문이며, 5~7단계도 같은 형태를 따릅니다.

## WASM 층은 선언에서 모든 산출물을 만든다

`wasm/`은 자체 `Project.toml`을 가진 빌드 환경입니다(WasmTarget.jl, JSON, 경로 의존성 GridToPINN).
단계마다 `wasm/entries/stepN.jl` 한 파일이 다음을 선언합니다.

- 진입점 함수: `T`에 대해 일반적이며 정수 인자는 `Int32`입니다.
- 내보낼 함수 목록: 인자 이름과 종류, 반환 종류, 설명, 대응하는 커널 정의.
- 조작 값: 이름, 단위, 기본값, 범위.
- 대안 지점: 선택 인자와 선택지. 선택지마다 대응하는 커널 함수.
- 일치 검사 사례: 호출 순서. 모든 내보내기와 모든 선택지, 깨뜨리기 입력을 포함해야 빌드가 통과합니다.

`wasm/build.jl`은 이 선언에서 단계별로 세 파일을 만들고 `index.json`에 등록합니다.

| 산출물 | 내용 |
|---|---|
| `stepN.wasm` | 함수마다 `<이름>_f64`, `<이름>_f32` 두 벌 |
| `stepN.json` | 목록 파일. 소스 줄 범위는 커널 파일을 파싱해 채운다 |
| `stepN.parity.json` | 일치 검사 사례와 네이티브 Julia 기대값 |

산출물은 `web/static/wasm/`에 쓰이고 git에 넣습니다. 그래서 Julia 없이도 웹을 빌드하고 배포할 수 있습니다.
대가는 소스와 산출물이 어긋날 수 있다는 점이며, CI가 `wasm/build.jl --check`와 일치 검사로 막습니다.
커널이나 선언을 고쳤으면 다시 빌드해 산출물을 함께 커밋합니다.

진입점에 수치 코드를 넣지 않는 것은 검토 규칙입니다. 커널이 컴파일되지 않으면 진입점에서 다시 구현하지 않고
커널을 고칩니다. 실제로 한 번 그렇게 했습니다. `integrate`가 걸음마다 `push!`를 쓰면 WASM에서 실행 시간이
걸음 수의 제곱으로 늘어서, 커널이 배열을 미리 잡도록 바꿨습니다.

## 웹 층은 목록 파일만 읽는다

`web/src/lib/gridtopinn/`은 순수 TypeScript 연결 모듈입니다. Svelte를 가져오지 않고, 불러오는 시점에
브라우저 전역을 건드리지 않습니다. `index.json`과 `stepN.json`을 읽어 함수를 이름으로 찾기 때문에
단계가 늘어도 코드를 고치지 않습니다. 무거운 계산은 같은 모듈의 Worker 래퍼로 돌립니다.

화면에 보이는 소스는 `src/**/*.jl` 파일 자체입니다. `web/src/lib/sources.ts`가 Vite의 `?raw` 가져오기로
읽고, 목록 파일의 줄 범위로 잘라 냅니다. 표시용 사본은 없습니다.

## 화면은 단계마다 컴포넌트 하나와 등록 한 줄로 늘어난다

라우트는 홈 카드(`/`), 단계 화면(`/step/1`~`/step/9`), 시험 페이지(`/verify`) 셋입니다. 1~3단계는 체험
화면이고, 목록 파일에 없는 4~9단계는 "준비 중" 자리표시자를 보입니다.

체험 화면은 `web/src/lib/experiments/`에 있습니다. 단계마다 `StepN.svelte` 하나와 `registry.ts`의 한 줄이
필요합니다. 조작 요소(슬라이더, 대안 선택, 정밀도)와 코드 줄 범위는 목록 파일에서 만들어지므로 화면에 수치
커널을 다시 쓰지 않습니다. 해, 오차, 정답은 모두 `step.fn(...)`이나 Worker가 돌려준 값입니다.
1, 2단계는 계산 결과를 애니메이션으로 재생하고(`playback.svelte.ts`, `reveal.ts`), 3단계는 Worker에서 한
프레임씩 돌며 그립니다(`runner.svelte.ts`).

통과 기준은 목록 파일이 아니라 `web/src/lib/experiments/config.ts`의 `PASS`에 있습니다. 값은 제안이며
측정으로 정한 것이 아닙니다. 공용 부품은 `web/src/lib/ui/`, 시험 페이지 부품은 `web/src/lib/verify/`입니다.
두 칸 배치는 1280px부터, 사이드바는 768px 미만에서 서랍으로 바뀝니다.

## 검증은 세 겹이다

| 겹 | 명령 | 확인하는 것 |
|---|---|---|
| 네이티브 | `Pkg.test()` | 정답, 수렴 차수, 깨뜨리기, Float32/Float64 타입 유지 |
| WASM 대 네이티브 | `node wasm/check_parity.mjs`, `bun run test` | 모든 내보내기와 대안이 네이티브와 같은 값을 내는지 |
| 브라우저 | `bun run test:e2e` | 빌드한 사이트가 실제로 뜨고, 같은 검사를 Chrome에서 통과하는지 |

같은 일치 검사 사례를 Julia, Node, 브라우저가 모두 실행합니다. 사례를 한 번 쓰면 세 곳에서 확인됩니다.

## 이 구조가 맞지 않는 경우

- 9단계(GPU)는 브라우저에서 돌지 않으므로 `wasm/`과 `web/` 층을 쓰지 않습니다. 별도 환경이 필요합니다.
- 8단계에서 미리 학습한 가중치를 정적 파일로 줄 경우, 목록 파일 스키마에 항목을 더해야 합니다.
- 2차원 장의 전달 비용이 문제가 되면(7단계) 값 하나씩 꺼내는 방식을 다시 검토해야 합니다.
  현재 측정값은 [calling-convention.md](calling-convention.md)에 있습니다.
